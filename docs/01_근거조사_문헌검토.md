# 01. 단계별 산출물 작성 방식: 문헌·공식 자료 검토

- 조사 기준일: **2026-10-26**
- 범위: 공식 플랫폼 문서, 국제표준 개요, NASA 엔지니어링 실무 가이드, 산업 가이드, 2026년 연구/프리프린트.
- 근거 표시: **[공식 실무]** / **[표준·기관]** / **[실증 연구]** / **[프리프린트]** / **[VibeLabs 제안]**.
- 주의: ISO 29148의 공개 *초록*만 확인했다. 유료 전문에 담긴 세부 조항을 확인했다고 주장하지 않는다.

## 1. 결론 요약

1. Anthropic 플레이북은 **Plan → Design → Build → Test → Deploy → Maintain**를 잇는 버전 관리 산출물(의도·명세·계획·코드/테스트·리뷰·인시던트)을 제시한다. 목적은 문서량 증가가 아닌 자동 인수인계를 통한 병목 축소다. [공식 실무, S1]
2. 소프트웨어 공학의 오래된 해답은 **검증 가능하게 쓴 요구사항, 양방향 추적성, 사전에 정한 검증 방법, 결함 수정의 증거**다. AI가 작성 주체가 되어도 이 원칙은 유효하다. [표준·기관, S3/S4]
3. Google Research의 2026년 논문은 LLM이 코드에서 테스트를 바로 생성하기보다 **사전 조건·사후 조건·미정의 동작을 먼저 정리**하도록 할 때 버그 탐지에서 개선을 보고했다(비교 실험: 탐지율 +9.8%p, 브랜치 커버리지 +2.5%p). 특정 실험의 결과이며 모든 프로젝트에서 보장되는 값은 아니다. [실증 연구, S6]
4. 2026년 GTDD 프리프린트는 **별도 테스터가 각 후보 구현 이후 새로운 반례를 생성**하고, 신뢰 가능한 평가기가 결과를 기록하는 접근을 제시한다. 고정된 테스트를 학습하여 통과하는 문제를 완화하려는 시도다. 아직 특정 과제의 제한된 실험이므로 일반화에는 주의한다. [프리프린트, S7]
5. 기존 GitHub Spec Kit은 명세 보완(clarify), 사양 품질 검사(checklist), 산출물 간 일관성 분석(analyze), 구현 후 누락 탐지(converge)를 이미 제공한다. **우리는 도구의 존재 자체가 아니라 QC·증거·권한 체계로 차별화**해야 한다. [공식 실무, S2]

## 2. 단계별 작성 절차: 근거 → 설계적 적용

### 2.1 Plan — `intent.md`

**근거**: Anthropic은 아이디어 제안자(또는 티켓·인시던트)가 일상어로 설명한 문제를 Claude와 대화해 proto-spec 형태의 `intent.md`로 만든 뒤, 원 제안자가 오해를 바로잡고 PO가 승인하도록 안내한다. 예시 핵심 항목은 Problem, Proposed outcome, Affected users and systems, Constraints, Open questions. [S1]

**작성 권장 절차 [제안]**
1. 기존 이슈·코드·업무용어·제약을 먼저 조사하고, `출처: 사용자 발언/기존 시스템/AI 제안/정책`을 구별한다.
2. 해결하려는 문제와 성공 시 변화를 1~2문단으로 재진술한다.
3. 구현 결과를 실질적으로 뒤바꿀 질문만 1~2개씩 순차 질문한다. `사용자 확정/미확정/가정`으로 기록한다.
4. 범위·비범위·제약·성공신호·열린 질문을 정리하고 초안의 오해를 확인받는다.
5. PO 승인 후 Git/PR에 커밋하며 **승인 기록을 파일의 `status` 텍스트만으로 대체하지 않는다.**

**품질 기준**: 과거 상태와 목표 상태가 구별됨, 사용자/영향 시스템 식별, 모순 없음, 핵심 결정의 소유자 지정, 추측을 사실로 기록하지 않음.

### 2.2 Design — `spec.md` 및 `traceability.md`

**근거**: Anthropic은 승인된 의도에 조직 정책 스킬을 적용하여 요구사항·설계 명세로 변환하고, 충돌을 정책 소유자에게 전달하라고 한다. ISO/IEC/IEEE 29148:2018은 요구사항 공학 프로세스와 정보 항목의 내용·형식을 다룬다(공개 초록 확인). NASA는 요구사항의 작성 품질, 양방향 추적, 검증 방법, 변경 관리를 강조한다. [S1/S3/S4]

**작성 권장 절차 [제안]**
1. `INT-xxx` 요구에서 기능 요구 `REQ-F-xxx`, 비기능 요구 `REQ-N-xxx`를 도출한다.
2. 각각 단일 행동 또는 검증 가능한 속성으로 작성한다. `해야 한다`와 조건·성능 목표·예외를 분명히 한다.
3. 상태전이, 정상/경계/음성 경로, 동시성, 실패복구, 권한·데이터 이동·개인정보·접근성을 분석한다.
4. API 계약/데이터 스키마·용어집·프로토타입을 필요에 따라 첨부한다.
5. 각 REQ의 근거 원본, 중요도, 결정자, 검증 가능한 기대값을 추적성 표에 올린다.
6. 모호하거나 충돌하는 정책은 `BLOCKED`로 두고 해당 정책 소유자가 해결하기 전 진행하지 않는다.

**품질 기준**: 중복·모순·추측이 없고, 모든 필수 REQ는 식별자와 확인 가능한 결과를 가진다.

### 2.3 Build Planning — `plan.md`

**근거**: Anthropic은 Plan Mode에서 코드 수정 전 설계를 검토하며 파일 목록·작업 순서·위험·증명 방법을 남길 것을 권장한다. 다른 엔지니어가 대화 없이도 구현할 수 있어야 한다. 계획 이탈 시 `plan.md`를 갱신하고 리뷰한다. [S1]

**작성 권장 절차 [제안]**
1. 기존 코드베이스 탐색 → 영향 범위/호환성/마이그레이션 파악.
2. 대안과 선택 근거, 의존성, 변경 파일/모듈, 작업 순서, 롤백 가능성, 불확실성을 작성.
3. 작업마다 `TASK-xxx`와 구현될 `REQ-xxx`를 연결한다.
4. `TASK`가 요구사항 전체를 다루는지 QC가 독립 감사한다.
5. 작업 계획과 QC 명세를 서로 교차 검토하고 승인 후 기준선 고정.

**주의**: Plan은 테스트 판정의 유일한 진실이 아니다. 잘못된 Plan이 그대로 검증되는 자기충족 오류를 피하기 위해 QC의 판단 근거는 **승인된 Spec**이 우선이다.

### 2.4 Test Design — `test-spec.md` (VibeLabs 확장)

**근거**: NASA 검증 매트릭스는 요구사항마다 검증 방법·절차·결과·편차를 추적할 것을 권장한다. Cucumber Gherkin은 Given/When/Then 형태의 관측 가능한 조건-행동-결과를 표현한다. Google의 2026년 실증 연구와 GTDD 프리프린트는 사전 계약과 별도 검증의 유용성을 시사한다. [S4/S5/S6/S7]

**작성 권장 절차 [제안]**
1. Builder와 별도의 **QC 설계 에이전트**에게 *승인된 `intent.md` + `spec.md` + 인터페이스 계약*만 우선 전달한다.
2. 각 REQ별 사전조건(precondition), 행동(action), 사후조건(postcondition), 불변조건(invariant), 허용·금지 상태를 분해한다.
3. 정·역방향 테스트와 경계값, 경쟁조건, 실패 주입, 접근권한, 회귀 범위를 정한다.
4. `TC-xxx → REQ-xxx`를 확정하고 실행 방법(단위/API/E2E/수동/정적/보안)·기대 결과·증거 형식 정의.
5. QC와 Planner가 **누락된 요구사항·모호한 합격 기준**을 교차 감사한다. Plan을 참고해 구현 가능성만 점검하고 테스트 오라클은 구현에 맞추지 않는다.
6. 테스트 명세는 구현 시작 전에 기준선화하며 Builder는 **수정 제안만 가능**, 원본 기준 변경은 승인된 별도 경로로 진행.

**검증 오라클 주의**: 테스트의 기대결과가 실제 사용자 의도와 맞는지 사람이 표본·핵심 시나리오를 승인해야 한다. 다른 에이전트가 작성했다고 자동으로 정답이 되지는 않는다.

### 2.5 Build — 코드·자체 테스트·작업 로그

**근거**: Anthropic은 빌드/린트/테스트와 UI 캡처를 에이전트 피드백 루프 안에 두고, 반복되는 오류는 `CLAUDE.md`·스킬에 반영하도록 한다. [S1]

**작성 권장 절차 [제안]**
1. 승인된 계획의 TASK 단위 구현, 작은 커밋, 자가 검증.
2. Builder 자체 테스트는 자유롭게 추가하되 잠금된 QC 수용 테스트는 수정 불가.
3. 계획 외 변경 발생 시 작업 중지 및 영향 분석 → 승인된 수정 계획 작성.
4. 실행한 명령·종료코드·로그·아티팩트·커밋을 증거로 저장.

### 2.6 Independent QC — `qc-report.md`, `defects/BUG-xxx.md`, `evidence/`

**근거**: Anthropic은 새로운 컨텍스트의 verifier 서브에이전트를 구현자의 가정과 분리해 최종 검증에 활용한다. NASA는 검증 방법·조건·사용 도구·결과·편차·조치·제품/명세 버전의 기록을 요구하는 형태를 제시한다. [S1/S4]

**작성 권장 절차 [제안]**
1. 별도 컨텍스트의 QC가 `spec`, `test-spec`, 커밋 SHA를 읽는다.
2. 사전 합의한 테스트 + 새로 생성한 탐색/적대적 테스트를 수행한다.
3. 실패 시 기대/실제/재현절차/로그/우선순위/관계 REQ/TC/빌드 SHA로 결함 티켓 생성.
4. Builder는 코드 수정(기존 잠금 수용 테스트 수정 금지) 후 새 SHA로 재검증 요청.
5. QC가 원래 실패 시나리오+이웃 경로+전체 관련 회귀 테스트를 다시 실행하고 결함을 검증 종료.
6. 요구사항 결함이면 `spec`으로 돌아가 새 기준선과 재승인을 거친다. 실패했다고 테스트 기대값을 무단으로 내리지 않는다.

**종료 조건**: 모든 `must` 요구사항에 유효한 증거, 미해결 차단 결함 0, 재현 불가/flaky 격리 절차를 정하고 증거에 기록, 승인된 변경만 포함.

### 2.7 Deploy — `review.md`, `release.md`

**근거**: Anthropic은 PR 리뷰에 AI를 활용하지만 인적 책임은 중요한 변경의 위험 수용과 배포 승인에 둔다. GitHub 브랜치 보호는 승인 리뷰·필수 상태 검사·우회 금지 설정을 제공한다. [S1/S10]

**작성 권장 절차 [제안]**
1. Plan↔실제 diff와 Spec↔test evidence를 각각 대조.
2. 위험 등급(low/medium/high)별 지정된 승인자.
3. CI 필수 체크, 민감 경로에 CODEOWNERS, 환경 승인/배포 권한 제한.
4. 배포 버전·배포자·시간·관측값·롤백 경로와 사전 리허설 증거 기록.

### 2.8 Maintain — `incident.md` → 새 `intent.md`

**근거**: Anthropic은 결정적 모니터링으로 임계값을 판단하고 위험도별로 진단·PR 생성·사전 승인 런북만 허용하는 패턴을 제시한다. Google SRE는 SLO·경보·인시던트 대응·사후 학습을 체계화한다. [S1/S11]

**작성 권장 절차 [제안]**
1. 사람이 정한 SLO/알람 규약과 결정적 탐지기 운영; 모델은 감지기가 아니다.
2. 인시던트 ID, 발생 시각, 관측값, 사용자 영향, 배포 SHA, 타임라인, 대응/승인자 기록.
3. 증거 기반 진단과 사전 승인된 복구 수단만 허용.
4. 원인/확실성/재발 방지/추가 검증 시나리오 기록.
5. 문제별 새 `intent.md`를 작성하고 과거 장애 시나리오를 회귀 평가에 추가.

## 3. 자료별 기여도와 해석 경계

| 자료 | 설계에 채택할 내용 | 채택 시 주의 |
|---|---|---|
| Anthropic SDLC [S1] | 6단계 + 커밋된 산출물 + 승인 경계 | 범용 표준이 아닌 기업 실무 플레이북 |
| GitHub Spec Kit [S2] | 명세 명료화·체크리스트·교차 분석·수렴 | 원형 워크플로는 우리 제품과 동일하지 않음 |
| ISO 29148 개요 [S3] | 요구사항 공학·정보 항목·형식화 필요성 | 원문 전문의 구체 조항을 검증한 것은 아님 |
| NASA [S4] | 양방향 추적·검증 계획·불일치 기록 | 항공우주 수준의 모든 절차를 소프트웨어에 강제하지 않음 |
| Cucumber [S5] | Given/When/Then, 외부에 관측되는 결과 | Gherkin 자체가 완전한 테스트 구현은 아님 |
| Google Research [S6] | 계약 선행 테스트 생성 | 제한된 벤치마크; 모든 프로젝트에 개선폭 일반화 금지 |
| GTDD [S7] | 독립 tester + 새로운 반례 + 회귀 저장 | 프리프린트·제한 실험·적대적 테스트 비용 |
| Claude Skills/Agents/Hooks [S8/S9] | 재사용 규칙·독립 컨텍스트·행동 인터셉트 | 프로젝트 수준 파일만으로 강한 보안 보장 불가 |
| GitHub [S10] | 강제 승인·상태 검사·경로 보호 | 리포지터리 권한과 설정이 필수 |
| Google SRE [S11] | 관측·인시던트 대응·사후 학습 | 1σ/2σ/3σ는 Anthropic 사례이지 범용 SRE 법칙 아님 |
