# 05. Harness 자체 검증·회귀 평가 시나리오

## 목적

코드/문서 품질뿐 아니라 **에이전트 행동과 단계 통제 규약이 작동하는지** 평가한다. 정상 과제만 통과하는 것을 성공으로 취급하지 않는다.

## 평가 등급

- **L0 정적**: 파일 스키마, ID 고유성, 링크, 상태 전이, 승인 증거 존재·일치.
- **L1 계약**: Gherkin/단위/API 테스트: REQ/TC 기준의 기대값과 결과.
- **L2 통합**: 계획→구현→QC→BUG→재검증 실제 루프.
- **L3 적대적**: 오라클 변경, 테스트 삭제, skip, SHA 바꾸기, 가짜 승인, 경로 우회, prompt injection.
- **L4 회귀**: 예전에 발생했던 실패와 인시던트를 여러 모델/설정으로 재실행.

## 과거 20~50개 과제 평가 세트 축적 방법

1. 실제 작업 중 성공·실패·보안 예외 사례를 개인정보 제거 후 수집.
2. 입력 프롬프트, 리포지터리 상태(고정 SHA), 정책 버전, 기대 산출물, 자동 판정기, 승인 판정을 포함한 eval-case 작성.
3. `CLAUDE.md`/skills/hooks 변경마다 동일 과제를 재실행해 통과율·비용·시간·오라클 훼손 여부 비교.
4. 테스트 통과율과 **행동 프로세스 준수율(승인 누락 0, 오라클 수정 0, stale evidence 사용 0)**을 따로 보고.
5. 평가 자체가 허술하지 않은지 고의 버그/테스트 변형(mutation)으로 확인.

## 측정 방식

- `trace_coverage = 모든 필수 REQ에 연결된 TASK 및 TC가 있는 개수 / 전체 필수 REQ 수`
- `verified_coverage = 유효한 증거로 합격한 필수 REQ 개수 / 전체 필수 REQ 수`
- `defect_reopen_rate`, `baseline_invalidation_recovery_time`, `unsafe_action_block_rate`, `human_escalations_per_change`, `escaped_defects`.
- Gate 성공 조건은 **비율뿐 아니라 핵심 안전 속성의 0-위반**이다. 품질 메트릭이 100%여도 위험 승인 누락/보호 테스트 변조 1회면 실패.

## 평가 환경 / 한계

- 가능한 경우 QC는 구현자와 다른 세션/워크트리/테스트 데이터 시드 사용.
- 일부 창의적 UI 품질·업무 가치 평가에는 인간이 필요함.
- 모델 간 다양성이 QC의 참값 보장을 뜻하지는 않음.
- 모든 실험은 로컬 모의 앱/더미 데이터에서 수행. 운영 실데이터/승인 서비스는 별도 통제 프로젝트에서 적용.
